## Abstract

PACT (Provenance Attestation and Chain of Trust) is an open protocol for establishing verifiable, privacy-preserving chains of institutional trust from cryptographic signatures already embedded in existing email infrastructure. PACT processes DMARC Aggregate Reports (rua=) — a standard reporting mechanism already generated by every major mail server in the world — to build an append-only Merkle tree of domain-level attestations, derive organic trust scores, and detect infrastructure anomalies, all without ever accessing, processing, or storing any message content, recipient identity, or personal data of any kind.

PACT is signature-primitive agnostic. The reference implementation is sourced exclusively from DMARC aggregate reporting, the universally deployed email authentication reporting standard. The protocol is designed from the outset to incorporate S/MIME, DKIM2, post-quantum signatures, and any future signing primitive that meets the protocol's attestation interface.

The result is a decentralized domain provenance layer — the trust cornerstone on which applications requiring richer semantics (document verification, compliance certification, KYC, anti-spam) can be built. PACT itself requires no participation from senders beyond a single DNS field addition, no behavioral change from verifiers, no message content access, and no trusted third party to adjudicate authenticity claims. It is the TCP/IP of institutional email trust: narrow, blind to content, and universally applicable.

This specification combines the v0.2 Merkle / encoding / threat-model work with the live `pact-score-0.1` formula and display rules. Implementation-specific details (D1, Base Sepolia, Cloudflare) are in Appendix B.

## 1. Motivation

### 1.1 The Broken Trust Model

Every institution in the world communicates via email. Every outbound email from an institutional domain is automatically cryptographically signed by the sending mail server using DKIM — a process that has operated silently and universally since 2011. This signature binds the sending domain to the exact content of the message at the moment of transmission. It is, in effect, an accidental notarization performed at global scale.

DMARC (Domain-based Message Authentication, Reporting, and Conformance) extends this further: every receiving mail server that validates a DKIM signature already generates a structured aggregate report describing that validation event and sends it to the domain owner. These reports are generated today, by billions of email deliveries, across every major mail server in the world.

Neither the DKIM signature nor the DMARC aggregate report has ever been systematically captured, persisted, or chained into a provenance layer.

The consequence is a world where:

- A payslip from payroll@company.com is indistinguishable from a fabricated PDF after the signing key rotates.
- A contract confirmation from deals@counterparty.com can be repudiated with no cryptographic recourse.
- A wire instruction from a compromised account at a legitimate domain passes every authentication check.
- An invoice altered between receipt and payment leaves no forensic trail.
- A domain impersonated by a lookalike (wise-payments.com vs wise.com) has no verifiable history that distinguishes it from the legitimate domain.

Generative AI accelerated this crisis. Documents that previously required skill and time to fabricate are now generated in seconds. In November 2024, FinCEN issued Alert FIN-2024-Alert004 explicitly identifying AI-generated synthetic financial documents as an active and growing threat to the US financial system. No corresponding technical standard exists to address it.

### 1.2 What PACT Provides

PACT provides three guarantees that no existing system provides simultaneously:

**Domain Provenance** — A verified, tamper-evident record that a specific institutional domain has been sending cryptographically authenticated email at a specific volume, from specific infrastructure, continuously over a specific period of time. This record cannot be fabricated retroactively.

**Anomaly Detection** — Statistical monitoring of each domain's authentication patterns derived from aggregate report data. Deviations from established baselines — unusual failure spikes, unrecognized sending infrastructure, lookalike domain activity — are detected and surfaced without accessing any message content.

**Organic Trust** — A mathematically derived trust score for each domain, computed from the volume, diversity, and maturity of its verified authentication history. No authority assigns this score. It emerges from observable reality.

### 1.3 The Privacy-First Constraint

PACT is designed around a non-negotiable privacy constraint:

**PACT never accesses, processes, transmits, or stores any message content, message subject, recipient identity, sender email address, or any personal data of any kind.**

This is not a policy commitment. It is an architectural guarantee enforced by the data source itself. DMARC aggregate reports contain only authentication metadata — domain names, IP addresses, DKIM pass/fail results, message counts, and time periods. They contain no message content, no subject lines, no recipient addresses, and no personally identifiable information.

PACT processes only aggregate reports. The privacy guarantee is therefore structural, not contractual.

### 1.4 What PACT Is Not

PACT is a domain provenance protocol. It is not a document authentication protocol. This distinction is fundamental.

PACT answers the question: "Is this domain a legitimate institutional sender with a verified history of authenticated email activity?" It does not answer: "Is this specific email or attachment authentic and unaltered?"

Applications that require document-level or message-level proof — legal evidence certification, invoice authentication, individual email verification — can be built on top of PACT, using the domain trust score as a cornerstone trust signal. These are separate products that consume the PACT protocol. They are not part of the PACT protocol itself.

This boundary exists for a reason. Domain provenance from aggregate reports is structurally privacy-preserving. Message-level proof requires access to individual message data — a fundamentally different privacy model that requires explicit user consent and is outside the scope of this specification.

### 1.5 The Layered Ecosystem Model

PACT follows the same architectural principle as the internet protocol stack: a base layer that is deliberately narrow, blind, and universal, on top of which applications with richer semantics are built.

```
LAYER 2 — APPLICATIONS (not standardized in this document)
  Built by anyone, consuming PACT Protocol as infrastructure.
  Exact design and privacy models specified separately.

  PACT Proof    — Document-level authentication
                  with explicit user consent.

  PACT Signal   — Real-time anomaly detection for
                  connected domains.

  PACT Chain    — Portable domain provenance credential
                  for compliance and onboarding.

──────────────────────────────────────────────────
LAYER 1 — PACT PROTOCOL (this specification)
  Domain provenance from DMARC aggregate reports.
  No message content. No personal data. Ever.
  Structurally private. Universally applicable.
──────────────────────────────────────────────────
LAYER 0 — EXISTING INFRASTRUCTURE (unchanged)
  DKIM signing by sending mail servers.
  DMARC aggregate reporting by receiving servers.
  DNS public key publication by domain owners.
  No changes required from any existing actor.
```

Layer 2 applications illustrated in Section 8 are ecosystem context only. They are not standardized here; their exact design and privacy models will be specified in separate application specifications.

## 2. DMARC as the Data Source

### 2.1 What DMARC Aggregate Reports Contain

DMARC aggregate reports (rua=) are XML documents generated and sent every 24 hours by receiving mail servers to the domain owner. They are already being generated today by every major mail provider — Gmail, Outlook, Yahoo, and others — for every domain that has published a DMARC record.

Each report contains:

```xml
<report_metadata>
  <org_name>google.com</org_name>
  <email>noreply-dmarc-support@google.com</email>
  <report_id>2026061401</report_id>
  <date_range>
    <begin>1718323200</begin>
    <end>1718409599</end>
  </date_range>
</report_metadata>
<record>
  <row>
    <source_ip>209.85.220.41</source_ip>
    <count>1247</count>
    <policy_evaluated>
      <disposition>none</disposition>
      <dkim>pass</dkim>
      <spf>pass</spf>
    </policy_evaluated>
  </row>
  <identifiers>
    <header_from>wise.com</header_from>
  </identifiers>
  <auth_results>
    <dkim>
      <domain>wise.com</domain>
      <selector>google-2024</selector>
      <result>pass</result>
    </dkim>
  </auth_results>
</record>
```

This contains: the sending domain (`header_from`), the DKIM selector used, the result of validation, the sending IP, the message count, the reporting organization (`org_name`), and the reporting period (`date_range`). It contains nothing about the content, subject, recipients, or any personally identifiable information.

**Reporter identity:** For trust scoring and diversity computation, the reporting organization is identified by the normalized `org_name` field from `report_metadata`. The envelope SMTP sender is used only for source authentication (Section 3.1.1), not as the reporter identity.

### 2.2 How a Domain Connects to PACT

A domain operator adds PACT as a co-recipient of their DMARC aggregate reports by adding a single address to their existing DNS record:

```
BEFORE:
_dmarc.wise.com TXT
  "v=DMARC1; p=reject; rua=mailto:dmarc@wise.com"

AFTER:
_dmarc.wise.com TXT
  "v=DMARC1; p=reject;
   rua=mailto:dmarc@wise.com,
       mailto:rua@webuildreal.dev"
```

That is the only change required. No software installation. No API integration. No SDK. No behavioral change for any sender or recipient. The receiving mail servers of the world — Gmail, Outlook, Yahoo — continue generating the same aggregate reports they always have. They now send a copy to PACT alongside the domain's existing destination.

### 2.3 Zero-Friction Onboarding

The reference implementation (`webuildreal.dev`) supports three onboarding paths:

- **Cloudflare OAuth** — one confirmation click; PACT adds the rua= field to `_dmarc` via API. Minimum scope: zone-scoped DNS edit for the target domain only.
- **Manual DNS** — one `_dmarc` field edit at any provider (GoDaddy, Namecheap, Route 53 console, etc.). The domain appears in the public record when the first valid aggregate report arrives — no extra registration step on the site.
- **Existing-tool forwarding** — add PACT as a report destination in an existing DMARC analytics tool (e.g. Postmark). Forwarded reports are authenticated per Section 3.1.1.

OAuth integrations MUST NOT read unrelated DNS records or modify fields other than `_dmarc`.

**Deferred:** Route 53 / AWS IAM cross-account DNS automation.

### 2.4 What PACT Does Not Use

PACT explicitly does not use and does not request access to:

- DMARC forensic reports (ruf=): these contain message-level data. PACT's privacy-first design excludes them entirely.
- Email content via IMAP, POP3, or any mailbox access protocol.
- Gmail API, Microsoft Graph API, or any mail provider API requiring OAuth scopes.
- Any message-level data whatsoever.

## 3. Protocol Operation

### 3.0 Normative Definitions

| Term | Definition |
|------|------------|
| **Sending domain** | The `header_from` domain in a DMARC aggregate report record, normalized per Appendix C.1. |
| **Reporting organization** | The normalized `org_name` from `report_metadata`. |
| **Reporting period** | The `(begin, end)` Unix timestamps from `report_metadata/date_range`. |
| **Leaf key** | The tuple `(domain, period_start, period_end, reporter_org)` that uniquely identifies a leaf slot before aggregation. |
| **Leaf** | A keccak256 commitment (Section 3.2) inserted at a monotonically increasing tree index. |
| **Reporter allowlist** | A curated set of authenticated reporting organizations and forwarding agents permitted to submit reports (Section 3.1.1). |

### 3.1 Data Ingestion

PACT operates a purpose-built SMTP receiver that accepts incoming DMARC aggregate reports. Upon receipt:

1. The report XML MUST be parsed and validated against the DMARC aggregate report schema (RFC 7489 Appendix C).
2. Source authentication MUST be performed per Section 3.1.1. Reports failing authentication MUST be discarded.
3. Per-domain authentication records MUST be extracted and normalized per Appendix C.
4. The raw report XML MUST be discarded after extraction. It MUST NOT be stored.
5. Extracted signals MUST be aggregated into leaf candidates per Section 3.2.1 before Merkle insertion.

#### 3.1.1 Report Source Authentication

Report source authentication prevents fake report injection and sybil attacks on trust scores. A report MUST pass all applicable checks before processing.

**Wrapper DKIM (required):** Cryptographically verify DKIM signatures on the RFC822 wrapper message (RFC 6376) — not the XML inside it. At least one passing signature's `d=` MUST match:

- **Direct:** an allowlisted DKIM domain for that report's `org_name` (e.g. Google `d=google.com`).
- **Forwarded:** an allowlisted forwarding-agent domain, only when `org_name` is a known reporter and the envelope sender is a forwarding agent — **or** the original reporter's `d=` still verifies on the forwarded wrapper.

Fail closed if no signature passes. Transient DNS failures while fetching the DKIM key SHOULD be retried, not treated as authentic. A forwarding agent's signature is a weaker witness than the reporter signing the wrapper itself; it proves the forwarder sent the message, not that Google or Microsoft did.

**Direct delivery** (SMTP envelope sender domain matches a known reporting organization):

1. Wrapper DKIM as above.
2. Validate SPF (or equivalent envelope authentication) for the connecting MTA.
3. Confirm the envelope sender's organizational domain matches an entry on the reporter allowlist, OR matches the `org_name` declared in the report metadata after normalization.
4. Reject reports where `org_name` and envelope sender domain are inconsistent without a documented forwarding relationship.

**Forwarded delivery** (Path B — DMARC analytics service forwarding):

1. Wrapper DKIM as above (`d=` on the forwarding-agent allowlist).
2. Confirm the forwarding agent (e.g., `reports.valimail.com`) is on the forwarding-agent allowlist.
3. Validate SPF for the forwarding agent's envelope sender.
4. Extract the original `org_name` from report metadata — this is the reporting organization for diversity and leaf construction, not the forwarder's domain.
5. Forwarded reports MUST NOT be attributed to the forwarding agent as the reporting organization.

**Reporter allowlist (v0.2):**

- Initially maintained by the first reference implementation (PBM Labs LLC).
- MUST include major mailbox providers: Google, Microsoft, Yahoo, Apple, and major ESPs generating DMARC aggregate reports at scale.
- MUST include approved forwarding agents: Valimail, Postmark, EasyDMARC, Dmarcian, and equivalent services.
- Transition to community-maintained allowlist with transparent governance is planned for v0.3 (Section 9.4).


**Reference implementation (August 2026):** Live ingest DKIM-verifies the wrapper (mailauth, DNS-over-HTTPS) before extracting XML. `validateReportSource` in `@pact/core` then requires a passing `d=` on the reporter or forwarding-agent allowlist, plus envelope-from / `org_name` consistency. The Worker does **not** independently SPF-check the connecting MTA (Cloudflare Email Routing has already accepted the message). Failed DKIM is discarded silently (no bounce to the reporter).

**Anti-abuse:**

- Rate-limit submissions per envelope sender and per `report_id`.
- Deduplicate on `(report_id, org_name, date_range.begin, date_range.end, header_from)` — duplicate submissions MUST NOT create additional leaves.
- Reject XML with implausible `count` values relative to reporter reputation (implementation-defined thresholds, subject to calibration).

### 3.2 Leaf Construction

#### 3.2.1 Leaf Granularity and Aggregation

**One leaf per leaf key per ingestion batch.** A leaf key is `(domain, period_start, period_end, reporter_org)`.

When multiple `<record>` rows within the same authenticated report share the same `header_from` and fall within the same `date_range`, they MUST be aggregated into a single leaf for that reporter and period:

- `dkim_pass_count` = sum of `count` where `policy_evaluated/dkim = pass`
- `dkim_fail_count` = sum of `count` where `policy_evaluated/dkim = fail`
- Selectors = union of all `auth_results/dkim/selector` values with `result = pass` or `fail`
- Source IPs = union of all `row/source_ip` values, each truncated to /24 per Appendix C.2

When multiple authenticated reports arrive for the same leaf key (e.g., a reporter resends or overlapping batches arrive), the processor MUST merge them idempotently:

- Add pass/fail counts
- Union selectors and IP ranges
- Retain the earliest seen `report_hash` components (Appendix C.3)

**Temporal ordering:** Trust scoring and anomaly detection MUST use `period_start` and `period_end` from the report, not ingestion order or tree insertion index. A leaf inserted later with an earlier reporting period MUST be scored against the period it attests to, not its position in the tree.

**High-volume domains:** Domains receiving reports from hundreds of reporters per period produce one leaf per reporter per period. This is expected. Volume scoring uses message counts (`V`), not leaf counts (Section 4.2).

#### 3.2.2 Leaf Hash

```
leaf = keccak256(
  domain_hash,      // Appendix C.1
  period_start,     // uint256: report_metadata/date_range/begin
  period_end,       // uint256: report_metadata/date_range/end
  reporter_hash,    // keccak256 of normalized reporter org_name
  dkim_pass_count,  // uint256
  dkim_fail_count,  // uint256
  selector_hash,    // keccak256 of canonical selector list (Appendix C.2)
  source_ip_hash,   // keccak256 of canonical IP range list (Appendix C.2)
  report_hash       // Appendix C.3
)
```

All fields except hashes are ABI-encoded as `uint256` in the order shown, then concatenated and hashed with keccak256. Hash fields are included as `bytes32` values. See Appendix C for canonical encoding rules.

keccak256 is used throughout off-chain processors and on-chain verifiers. Using the same hash function in both layers ensures Merkle inclusion proofs generated off-chain are verifiable on-chain without a dedicated proof verifier contract.

No message content. No recipient identity. No personal data. The leaf is a cryptographic commitment to authentication infrastructure activity over a time period.

**Sorting requirement:** Selectors and IP ranges MUST be canonically sorted before hashing (Appendix C.2). Different sort orders MUST NOT produce different leaf hashes for the same underlying data.

**Sub-commitments (deferred):** v0.2 commits to sorted aggregate hashes for selectors and IPs. v0.3 MAY introduce an internal Merkle sub-tree over `(selector, ip_range, pass_count, fail_count)` tuples within a leaf to enable selective disclosure for Layer 2 applications (e.g., PACT Chain) without revealing full leaf content.

### 3.3 Merkle Tree and On-Chain Anchoring

#### 3.3.1 Sparse Merkle Tree Specification

Leaves are inserted into an append-only sparse Merkle tree with the following normative parameters:

| Parameter | Value |
|-----------|-------|
| Hash function | keccak256 |
| Tree depth | 32 levels (supports ~4 billion leaves) |
| Leaf index | Monotonically increasing `uint32` assignment order at insertion time |
| Empty subtree hash | `ZERO_HASH[0] = 0x000...000`; `ZERO_HASH[i] = keccak256(ZERO_HASH[i-1], ZERO_HASH[i-1])` |
| Parent hash | `keccak256(left, right)` — left sibling first, right sibling second |
| Leaf position | `index` maps to path via standard sparse Merkle bit decomposition |

**Inclusion proof format:** An array of `bytes32` sibling hashes from leaf to root, with a `uint32` leaf `index` and the target `root`. Verifiers reconstruct the path using the index bit pattern. Proof length is exactly 32 elements.

**Root publication:** Merkle roots are published on-chain at regular intervals (default: daily, aligned with aggregate report cadence). Once published, a root is immutable.

**Verification:** Any party can independently verify that a specific leaf is a member of the tree by providing the leaf value, its insertion index, and a Merkle inclusion proof. Verification requires the published on-chain root and the leaf data. It does not require contacting the operating entity.

### 3.4 Anomaly Detection

Anomaly detection is a Layer 2 concern (PACT Signal) in product terms, but the protocol defines the signals available from aggregate report data. PACT continuously monitors the aggregate report stream for each connected domain and computes a rolling baseline of normal authentication behavior.

```
BASELINE PER DOMAIN (computed from historical leaves, keyed by period)
  - Normal DKIM pass rate (mean and standard deviation)
  - Known sending IP ranges (/24)
  - Known DKIM selectors in use
  - Normal daily message volume range
  - Normal volume distribution across reporting organizations

ANOMALY SIGNALS (derived from deviations from baseline)

TYPE 1 — Failure rate spike
  Alert when failure rate exceeds baseline mean by > 3 standard
  deviations in a single reporting period.

TYPE 2 — Unknown sending infrastructure
  Alert when DKIM failures originate from IP ranges not present
  in the domain's authorized set.

TYPE 3 — Unknown selector
  Alert when a DKIM selector not seen in the prior 90 days appears
  with associated failures.
  Suppressed during selector learning mode (Section 3.4.1).

TYPE 4 — Lookalike domain activity
  See Section 3.4.2.
```

All anomaly detection operates exclusively on authentication metadata from aggregate reports. No message content is accessed at any point in the detection pipeline.

Alerts are delivered to domain operators via notification channels configured at onboarding (email, webhook, or API). Alert delivery is outside the core protocol and is not required for interoperability.

#### 3.4.1 Selector Learning and Key Rotation

Legitimate DKIM key rotation introduces new selectors that TYPE 3 would otherwise flag. Implementations MUST support:

**Learning mode (default):** For the first 30 days after a domain connects, all selectors observed in authenticated reports are recorded as authorized. No TYPE 3 alerts are emitted during this period.

**Steady state:** After learning mode, new selectors are classified as:

- **Informational:** New selector, 0% failure rate, sending from known IP ranges — consistent with planned rotation. No alert, or low-severity notification only.
- **Alert:** New selector with failures, or new selector from unknown IP ranges — consistent with unauthorized sending.

**Pre-registration (optional):** Domain operators MAY announce planned selectors via an authenticated API. Pre-registered selectors MUST NOT trigger TYPE 3 alerts on first appearance.

#### 3.4.2 Lookalike Domain Detection — Scope and Methodology

Lookalike detection is probabilistic, not deterministic. Perfect detection of homograph attacks (e.g., Cyrillic homoglyphs) is an open research problem.

**Data sources available in v0.2:**

| Source | What it detects |
|--------|-----------------|
| Connected domain corpus | A lookalike domain that connects to PACT and accumulates a low trust score vs. the protected domain |
| Spoofing failures in connected domain reports | Third parties attempting to send as a lookalike domain, visible as DKIM/SPF failures in the protected domain's aggregate reports when the lookalike appears in `auth_results` or failure telemetry |
| Passive domain registration monitoring (optional) | Newly registered domains with Levenshtein distance ≤ 2 from a connected domain, or homograph-normalized equivalents — requires a separate DNS monitoring feed and is NOT derived from DMARC reports alone |

**Methodology:**

- String similarity: normalized Levenshtein distance ≤ 2 on punycoded domain labels.
- Homograph normalization: map confusable Unicode characters to ASCII equivalents before comparison (best-effort; not exhaustive).
- Registration recency: domains registered within 90 days with high similarity score are elevated.

**What v0.2 does NOT claim:** PACT cannot detect lookalike domain activity for domains that have not connected to PACT and do not appear in connected domains' failure telemetry, unless passive DNS monitoring is enabled. TYPE 4 alerts MUST be labeled with their data source.

## 4. Organic Trust Scoring

### 4.1 Principle: No Registry, No Governance, No Curation

Trust scores in PACT are not declared. They are not assigned by a committee. They are not stored in a registry. They emerge organically from the accumulated, verifiable authentication activity of real institutional senders as recorded in aggregate reports from the global mail infrastructure.

A domain with millions of verified DKIM-pass messages from diverse receiving mail servers over years of continuous history cannot be fabricated retroactively. The cost of attacking the trust score is identical to the cost of operating as a legitimate high-volume institutional sender for years.

### 4.2 Two Independent Clocks, Never Merged

A domain has two distinct ages that PACT MUST never collapse into one number: how long the domain itself has existed, and how long it has been generating verified PACT history.

```
DOMAIN AGE
  Source: public domain registration record (WHOIS
  creation date, or equivalent public registry data)
  Meaning: how long this domain name has existed
  Verifiable independently of PACT, by anyone

PACT HISTORY
  Source: days since the domain's first processed
  aggregate report
  Meaning: how long PACT has been accumulating
  verified authentication activity for this domain
  Only PACT can attest to this
```

A domain that has existed for eight years but connected to PACT today has a long domain age and a PACT history of zero. This is common and expected. Collapsing these two clocks into a single maturity number would let a hijacker inherit reputation from registration age on day one. Domain age is display context only. It MUST NOT enter the score arithmetic.

### 4.3 Trust Score Formula

The live algorithm identifier is `pact-score-0.1`.

The trust score is derived only from verified PACT history — volume, diversity, and the PACT-history maturity factor. Domain age is never an input.

For a given domain d at time t:

```
T(d, t) = log(V(d,t) + 1) × D(d,t) × A(d,t)

V(d,t) = Σ dkim_pass_count across all authenticated leaves
          for domain d where period_end ≤ t
         (sum of message counts — NOT leaf count)

D(d,t) = min(1, |R(d,t)| / leaf_count(d,t))
         (diversity coefficient, range 0 to 1)
         |R| = distinct reporter_org values
         leaf_count = number of authenticated leaves for d

A(d,t) = 1 - e^(-λ × pact_age(d,t))
         (PACT-history maturity factor, range 0 to 1)
         pact_age(d,t) = days since first authenticated leaf
                    for domain d
         λ = 0.005
         A(d,t) = 0.5 at ≈139 days
         A ≈ 0.90 at ~460 days
```

The v0.2 draft proposed `D = log(|R|+1)/log(50)`. That formula was **never shipped** and is not part of this specification.

**Logarithmic volume:** bulk inflation has sub-linear returns due to `log(V+1)`.

**Diversity coefficient:** rewards confirmation by many independent reporting organizations relative to the number of verified events. A domain whose history is concentrated in a single reporter scores lower than one confirmed across many orgs.

**PACT-history maturity factor:** a domain connected yesterday cannot reach high maturity regardless of volume. Primary defense against lookalike attacks and DNS hijack windows. MUST NOT be inflated by domain registration age.

### 4.4 Provisional vs. Activated Scores

Two score presentations are defined:

| Score | Formula | Label | Intended use |
|-------|---------|-------|----------------|
| **Raw score** | `T(d,t)` | "Provisional" / "Building" when `A(d,t) < 0.5` | Public transparency pages, early signal |
| **Activated score** | `T(d,t)` when `A(d,t) ≥ 0.5`; otherwise omitted or flagged | "Activated" / "Proven" | Third-party reliance, compliance submissions |

The activation threshold `A(d,t) ≥ 0.5` corresponds to approximately 139 days of continuous history. Implementations MUST display provisional status clearly when `A(d,t) < 0.5`.

Applications using PACT define their own acceptance thresholds. The protocol does not enforce any threshold.

The public reference UI leads with verified history (days, reports, reporting organizations) and treats the scaled score as a technical verification detail until the signal is meaningful (`pact-display-0.1`, §4.6).

### 4.5 Trust Score Interpretation

Thresholds are initial guidance subject to empirical calibration:

```
T < 1.0    No verified PACT history yet — this includes
           both brand-new domains and decades-old
           institutions that simply haven't connected
T 1-3      Early PACT history — early-stage signal
T 3-6      Established PACT history — moderate confidence
T 6-9      Long, high-volume PACT history — high confidence
T > 9      Extensive PACT history — maximum confidence
```

A score in the `T < 1.0` range MUST always be displayed together with the domain's registration age (Section 4.2), never alone.

Scores are not normalized percentiles. A domain's absolute score reflects its own history, not its rank relative to other domains.

### 4.6 Presenting the Score to Humans

The raw value of `T` is mathematically correct but not legible on its own. The formula in Section 4.3 is never altered for presentation. A separate display layer (`pact-display-0.1`) maps raw `T` onto a bounded 0–100 scale:

```
DISPLAY MAPPING (raw T → 0-100 shown to humans)

  T = 0          →  0 / 100   "No history yet"
  0 < T < 1.0    →  1-10 / 100  "Provisional"
  T 1-3          →  10-35 / 100  "Early"
  T 3-6          →  35-65 / 100  "Established"
  T 6-9          →  65-90 / 100  "High confidence"
  T > 9          →  90-100 / 100 "Maximum confidence"
```

The display layer MUST never round a nonzero raw score down to a 0/100 display value. The label **"No history yet"** is reserved exclusively for `T = 0`.

Changing how people see the score MUST NOT rewrite what was measured. Display mapping version MAY change without recomputing stored raw scores.

### 4.7 Communicating Progress, Not Just Position

The maturity factor's slow growth (λ = 0.005, reaching its ceiling over roughly two years) is a deliberate security property, not a UX defect. No display change SHOULD attempt to compensate by adjusting λ or any other term in the formula.

Any interface displaying a trust score in the `T < 3` range SHOULD also display:

```
- How long the domain has been accumulating PACT
  history (pact_age in days, distinct from domain
  registration age per Section 4.2)
- An estimate of the time remaining until the domain's
  current trajectory crosses into the next interpretation
  band, computed from the domain's current volume and
  diversity trend, not a fixed constant
```

## 5. Privacy Model

### 5.1 Structural Privacy Guarantee

PACT's privacy guarantee is structural, not policy-based. The guarantee holds because the data source — DMARC aggregate reports — contains no message content, no recipient addresses, and no sender mailbox identifiers. This cannot be changed by policy or misconfiguration at the message level, because that data never enters the pipeline.

### 5.2 What Is On-Chain (Public)

Each Merkle leaf commits to:

- `domain_hash` — keccak256 of the normalized sending domain. For any domain known to the verifier, this is trivially reversible by brute force over candidate domain names. This is by design: PACT is a provenance layer, not an anonymity layer.
- `reporter_hash` — keccak256 of the reporting organization name.
- The reporting period (`period_start`, `period_end`)
- Aggregate DKIM pass and fail counts
- `selector_hash` and `source_ip_hash` — commitments to sorted lists. Selectors are also public in DNS; IP ranges are brute-forceable over plausible /24 candidates. These hashes provide compact commitments, not cryptographic privacy.
- `report_hash` — auditability anchor to the source report (Appendix C.3)

### 5.3 Off-Chain Data Retention

Off-chain processors MAY retain granular `source_ip` values (full IPv4/IPv6, not truncated) and per-selector statistics for anomaly detection baselines. This data:

- MUST NOT include message content, subjects, recipients, or sender mailbox addresses.
- SHOULD be retained no longer than necessary for baseline computation (recommended maximum: 365 days).
- MUST be stored with access controls at least as restrictive as the reporter allowlist configuration.

IP addresses in DMARC aggregate reports may constitute personal data in some jurisdictions when they identify an individual's device. PACT's on-chain commitments truncate to /24. Off-chain retention policies SHOULD be reviewed by legal counsel for specific deployments.

### 5.4 What Is Never in the System

- Any message content (subject, body, attachments)
- Any recipient email address or identity
- Any sender email address (only the sending domain)
- Any personally identifiable information from message headers
- Any individual message identifier
- DMARC forensic report (ruf=) data

### 5.5 GDPR and Privacy Regulations

PACT processes domain-level authentication metadata explicitly designed for third-party consumption under the DMARC standard (RFC 7489). For typical institutional domains, this metadata generally does not implicate data subject rights. Edge cases exist: domain names incorporating natural person names, and IP addresses that may identify individuals in specific contexts.

Implementers SHOULD obtain legal counsel confirmation for their jurisdiction and deployment model. The protocol operator's privacy posture does not replace a deployer's obligations as data controller where applicable.

## 6. Domain Onboarding

### 6.1 The DNS Change

A domain connects to PACT by adding the PACT rua= address as a co-recipient in its DMARC DNS record. This is a standard DMARC mechanism explicitly defined in RFC 7489 — a domain may specify multiple rua= destinations separated by commas.

The domain's existing DMARC policy, reporting destinations, and email operations are entirely unaffected. PACT receives a copy of the same reports that are already being sent to the domain's existing destinations.

### 6.2 External Destination Verification

RFC 7489 requires that third-party report destinations verify their willingness to receive reports. PACT satisfies this by publishing a verification DNS record:

```
_report._dmarc.webuildreal.dev TXT
  "v=DMARC1"
```

This record is published once and authorizes all domains to send their DMARC aggregate reports to the PACT rua= address. No per-domain configuration is required on the PACT side.

### 6.3 Onboarding Paths

The reference implementation supports three paths (lowest friction first):

**Path A — Cloudflare OAuth**
Domain operator authorizes zone-scoped DNS edit. PACT reads the existing `_dmarc` record and adds the rua= field automatically.

**Path B — Manual DNS edit**
Domain operator adds the PACT rua= address (`rua@pact.webuildreal.dev`) to the `rua=` field of their existing `_dmarc` TXT record at any DNS provider. The public record is created automatically on the first valid aggregate report.

**Path C — DMARC service forwarding**
Operator adds PACT as a forwarding destination in an analytics service dashboard. Forwarded reports are authenticated per Section 3.1.1.

**Deferred:** OAuth for other DNS providers (e.g., AWS Route 53 via cross-account IAM).

### 6.4 Domain Control and Hijack Window

Connecting a domain to PACT demonstrates DNS control at connection time. A party with temporary DNS access could add the PACT rua= address and begin accumulating provisional history.

Mitigations:

- Raw scores during the first ~139 days are labeled provisional (Section 4.4).
- Activated scores require sustained history; brief hijack windows do not produce bank-grade trust signals.
- Removing the rua= entry stops new report flow; existing anchored leaves remain immutable but maturity stops increasing without new reports.

## 7. BEC Attack Coverage

### 7.1 What PACT Detects via Aggregate Reports

```
ATTACK TYPE              DETECTION MECHANISM
────────────────────────────────────────────────────────────
Domain Spoofing          Lookalike monitoring (Section 3.4.2).
                         New lookalike has low maturity and
                         volume vs. established domain.
                         Gap is immediate for connected domains.

Infrastructure Attack    Failure rate spike (TYPE 1) and unknown
                         IP detection (TYPE 2).
                         Detection within one reporting period
                         (~24h) of report receipt.

Key Compromise           Unknown selector with failures (TYPE 3).
                         Suppressed for planned rotations
                         (Section 3.4.1).

Volume Anomaly           Deviation from established volume baseline.
```

### 7.2 What PACT Does Not Detect via Aggregate Reports

**Account Takeover (BEC Modality 2):** When an attacker compromises a legitimate email account and sends from a legitimate domain with valid DKIM, the aggregate report shows a DKIM pass. PACT cannot distinguish this from legitimate traffic at the aggregate level.

This is an honest limitation of the privacy-first aggregate-only design. Detection of individual message-level anomalies would require access to message content or metadata, which PACT's privacy model explicitly prohibits.

### 7.3 Complete BEC Coverage Summary

```
BEC Modality             PACT Coverage (v0.2)
─────────────────────────────────────────────
Domain Spoofing          Strong (with connected domain +
                         optional DNS monitoring)
Infrastructure Attack    Strong (~24h detection)
Account Takeover         Not covered (by design)
Document Manipulation    Out of scope — Layer 2 with consent
```

## 8. Building on PACT Protocol

PACT Protocol provides domain provenance as a base layer. It deliberately stops at the domain level. Three named applications are defined in this ecosystem for illustration. **They are not standardized in this document.**

### 8.1 The Protocol Boundary

PACT Protocol's scope ends at domain-level attestation derived from DMARC aggregate reports. Anything requiring access to individual messages, email content, attachments, or recipient identity is outside the protocol and MUST be implemented as a separate application with its own privacy model and explicit user consent mechanisms.

### 8.2–8.4 Application Summaries (Informative)

**PACT Proof** — Document-level authentication with explicit user consent. User provides a specific .eml file. Validates DKIM. References domain trust score as corroboration. Separate application specification.

**PACT Signal** — Anomaly detection and alerting (Section 3.4). Delivers TYPE 1–4 signals to domain operators. Separate application specification.

**PACT Chain** — Packages Merkle inclusion proofs and trust history into a portable credential. Uses activated trust scores (Section 4.4). Separate application specification.

### 8.5 Shared Constraints for All Applications

All Layer 2 applications that go beyond domain-level provenance MUST:

- Require explicit, per-action user consent before accessing any individual message.
- Never operate passively or automatically on message content.
- Implement their own privacy model appropriate to their data access level.
- Never use automated or passive message interception.
- Reference PACT Protocol domain trust scores as supplementary signals, not as standalone proof of individual message authenticity.

## 9. Smart Contract Specification

The PACT smart contract is minimal by design. It records Merkle roots. It does not compute trust scores. It does not maintain registries. All trust scoring and anomaly detection is computed off-chain from leaf data verified against on-chain roots.

### 9.1 State

```solidity
struct MerkleRoot {
    bytes32 root;
    uint256 timestamp;   // block.timestamp at publication
    uint256 leafCount;   // total leaves included in tree at this root
}
MerkleRoot[] public roots;
```

### 9.2 Functions

```solidity
function publishRoot(
    bytes32 root,
    uint256 leafCount
) external;
// timestamp is set to block.timestamp at call time

function verifyProof(
    bytes32 leaf,
    uint32 index,
    bytes32[] calldata proof,  // exactly 32 sibling hashes
    bytes32 root
) external pure returns (bool);

function getLatestRoot()
    external
    view
    returns (bytes32 root, uint256 leafCount, uint256 timestamp);
```

### 9.3 Data Availability Assumption

**On-chain roots attest inclusion, not availability.** A verifier MUST obtain:

1. The leaf preimage (or its constituent fields to recompute the hash)
2. The leaf's insertion `index`
3. The Merkle inclusion proof
4. The on-chain root matching the proof

Leaf data is stored off-chain by one or more data providers. In v0.2, the reference implementation operates a single data provider. The on-chain root proves the leaf was committed; it does not guarantee that leaf data remains available. Verifiers SHOULD archive proofs they rely on.

**Long-term availability (v0.3):** Content-addressed storage (IPFS or equivalent), replicated data provider sets, and data availability sampling are under consideration.

### 9.4 Governance and Permissionless Transition

The smart contract has no upgrade mechanism. It is deployed once and is immutable.

**Live (August 2026):** `PactRoots` is deployed on **Base Sepolia** (Ethereum L2 testnet) at `0x873e76897BC3Fe8EBdfa67cb73404dA75B2d64ee`. Root publication is permissioned to the PBM Labs LLC operator key (Ownable2Step). A permissioned publisher can theoretically omit new leaves from publication but cannot alter previously published roots. This is **not** Base mainnet.

**Next:** Base mainnet with the same permissioned publisher, then permissionless root publication with economic stake requirements. Stake slashing conditions under consideration:

- Publishing a root inconsistent with the canonical off-chain leaf sequence
- Censoring leaves beyond a defined timeout window
- Failing to publish within N hours of the agreed cadence

Economic security model and slashing parameters are open for community input (Section 12).

## 10. Threat Model

### 10.1 Assumptions

PACT assumes:

- The underlying blockchain is censorship-resistant and provides immutable transaction ordering.
- keccak256 is collision-resistant.
- DMARC aggregate reports from allowlisted reporters are generated honestly.
- The domain operator who adds PACT to their rua= field controls that domain at onboarding time.
- Verifiers understand the data availability assumption (Section 9.3).

### 10.2 Out of Scope

PACT does not protect against:

- A domain operator who deliberately sends fraudulent email from their own domain.
- Receiving mail servers that generate false aggregate reports (mitigated by reporter allowlist, not eliminated).
- Account Takeover attacks (by design — privacy constraint).
- Domains that have not connected to PACT.
- Sophisticated homograph lookalike attacks (probabilistic detection only).

### 10.3 Attack Resistance

**Trust score gaming:** Generating false DKIM-pass volume requires controlling the sending domain's DKIM key and sending real email received and reported by allowlisted mail servers. Cost equals legitimate high-volume operation.

**Fake aggregate reports:** Reports without a passing wrapper DKIM `d=` on the reporter or forwarding-agent allowlist are discarded (Section 3.1.1). Deduplication prevents naive replay. The reference implementation does not independently SPF-check the connecting MTA. Forwarded reports are witnessed by the forwarder's DKIM, not the original reporter's.

**Receiver sybil attack:** A domain operator who operates or colludes with a reporting MTA could attempt to inflate `V` and `D` by submitting self-generated reports. Mitigated in v0.2 by the reporter allowlist. v0.3 SHOULD add per-reporter volume caps and reporter reputation weighting.

**Retroactive fabrication:** The Merkle tree is append-only. Leaf commitments use report period timestamps from authenticated reports, but insertion order is monotonic. A permissioned publisher could delay publication but cannot alter published roots.

**DNS hijack window:** Temporary DNS control produces only provisional scores until maturity threshold (Sections 4.4, 6.4).

**Publisher censorship:** A permissioned root publisher could omit leaves. Mitigated in v0.3 by permissionless publication and stake slashing. v0.2 mitigates by publishing daily roots with monotonically increasing `leafCount`, enabling auditors to detect gaps.

## 11. Relation to Existing Standards

**RFC 6376 (DKIM):** PACT uses DKIM authentication results as reported in DMARC aggregate reports. Fully compatible. No changes to DKIM infrastructure required.

**RFC 7489 (DMARC):** PACT is built on DMARC aggregate reporting. It uses the existing rua= mechanism exactly as specified. PACT is a consumer of DMARC reports, not an extension of DMARC.

**RFC 8460 (SMTP TLS Reporting):** Complementary. Both operate at infrastructure metadata level without message content access.

**RFC 5751 (S/MIME):** Applicable to Layer 2 applications requiring individual message-level attestation with explicit user consent. Not part of the core protocol.

**NIST PQC Standards (2024):** PACT's primitive-agnostic architecture accommodates post-quantum primitives in future versions.

**Federal Rules of Evidence 902(13) and 902(14):** Domain-level credentials (PACT Chain) are designed to support FRE 902(13) declarations. Message-level certificates (PACT Proof) are designed to support FRE 902(14). Legal counsel MUST confirm admissibility in specific jurisdictions.

**GDPR and privacy regulations:** See Section 5.5.

## 12. Open Questions for Community Input

1. **Diversity coefficient:** Is `reportingOrgs / leafCount` (live `pact-score-0.1`) sufficient, or should a later revision adopt HHI-based concentration scoring or a logarithmic cap?
2. **Per-reporter volume caps:** What cap prevents sybil inflation without penalizing legitimate high-volume reporters?
3. **Sub-commitment structure:** Should v0.3 define an internal Merkle tree over selector/IP tuples for selective disclosure?
4. **Proof system selection:** ZK proofs for aggregate statistics privacy — Groth16 vs. PLONK vs. STARKs. Not required for v0.2 Merkle proofs.
5. **Permissionless node operation:** Economic security model, stake size, and slashing conditions for v0.3.
6. **Cross-chain deployment:** Multiple chain root publication and canonical chain selection.
7. **Trust score calibration:** Empirical tuning of K, λ, and thresholds against a representative domain corpus.
8. **Decentralized data availability:** IPFS, erasure coding, or DA layer for leaf persistence without a single operator.
9. **Federation with DMARC analytics services:** Avoid redundant processing by accepting attestations from established DMARC vendors.
10. **Homograph detection:** Integration of Unicode TR39 confusable detection or external threat feeds.

## Appendix A: Glossary

**Activated score:** Trust score presentation when `A(d,t) ≥ 0.5` (~139 days history). Suitable for third-party reliance.

**Aggregate report (rua=):** Structured XML from receiving mail servers to domain owners, typically every 24 hours. RFC 7489. No message content.

**Leaf key:** `(domain, period_start, period_end, reporter_org)` — unique aggregation slot before hashing.

**Merkle inclusion proof:** Cryptographic proof that a leaf at a given index is a member of a tree with a given root.

**Organic trust score:** Computed metric from volume, diversity, and maturity. Not assigned — emergent.

**Provisional score:** Trust score when `A(d,t) < 0.5`. Visible but not suitable for high-stakes reliance.

**Reporter allowlist:** Curated set of authenticated reporting organizations and forwarding agents.

**Primitive agnosticism:** Trust infrastructure independent of the underlying signing mechanism.

## Appendix C: Canonical Encoding (Normative)

### C.1 Domain Normalization

1. Convert to lowercase ASCII.
2. Convert IDN labels to punycode (A-labels).
3. Strip trailing dot if present.
4. `domain_hash = keccak256(utf8_bytes(domain))`

### C.2 Selector and IP List Canonicalization

**Selectors:**

1. Collect all distinct selector strings from `auth_results/dkim` for the leaf key.
2. Normalize to lowercase.
3. Sort lexicographically (UTF-8 byte order).
4. Concatenate with `,` separator (no spaces).
5. `selector_hash = keccak256(utf8_bytes(canonical_string))`

**IP ranges:**

1. Collect all `source_ip` values for the leaf key.
2. Truncate IPv4 to /24: zero the last octet. IPv6: truncate to /48 (first 48 bits).
3. Format IPv4 as dotted decimal with last octet `0` (e.g., `209.85.220.0`).
4. Sort lexicographically by string representation.
5. Concatenate with `,` separator.
6. `source_ip_hash = keccak256(utf8_bytes(canonical_string))`

### C.3 Report Hash

```
report_hash = keccak256(utf8_bytes(
  reporter_org + "|" +
  report_id + "|" +
  period_start + "|" +
  period_end + "|" +
  domain
))
```

Where `reporter_org` and `domain` are normalized per C.1 (domain) and lowercase trimmed `org_name`.

### C.4 Leaf Preimage Encoding

```
preimage = abi.encodePacked(
  bytes32 domain_hash,
  uint256 period_start,
  uint256 period_end,
  bytes32 reporter_hash,    // keccak256(utf8_bytes(normalized org_name))
  uint256 dkim_pass_count,
  uint256 dkim_fail_count,
  bytes32 selector_hash,
  bytes32 source_ip_hash,
  bytes32 report_hash
)
leaf = keccak256(preimage)
```
